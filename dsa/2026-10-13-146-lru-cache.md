# DSA Interview Walkthrough — LeetCode 146: LRU Cache

**Difficulty:** Medium  
**Pattern:** Hash Map · Doubly Linked List · Data Structure Design  
**Core lesson:** When you need O(1) lookup plus O(1) updates to recency order, combine a hash map with a doubly linked list.

## 1. Interviewer prompt

Design an LRU cache with capacity `capacity` supporting:
- `get(key)`: return the value or `-1`, and mark the key as most recently used.
- `put(key,value)`: insert/update the key, mark it most recently used, and evict the least recently used key if capacity is exceeded.

Both operations must run in average `O(1)` time.

## 2. Recognize the pattern

A hash map gives O(1) lookup but does not maintain recency order.

A linked list maintains order but finding a key in it is O(n).

Combine them:

```text
Hash map: key -> linked-list node
Doubly linked list: LRU <-> ... <-> MRU
```

The map answers **where is the node?** The list answers **which node is oldest/newest?**

## 3. Why doubly linked?

When a key is accessed, its node may be anywhere in the list. We need to remove that node in O(1), which requires access to both its previous and next neighbors.

A singly linked list cannot remove an arbitrary node in O(1) unless we also know its predecessor.

## 4. Sentinel nodes

Use dummy `left` and `right` nodes:

```text
left <-> real nodes <-> right
```

- `left.next` is the least recently used real node.
- `right.prev` is the most recently used real node.

Sentinels eliminate special cases for empty lists and end insertions/removals.

## 5. Helper operations

`remove(node)` disconnects a node from the list.

`insert(node)` places a node immediately before `right`, making it most recently used.

When a key is accessed or updated:
1. remove its node,
2. insert it at the MRU end.

When capacity is exceeded:
1. remove `left.next`,
2. delete that key from the map.

## 6. Clean final Python solution

```python
class Node:
    def __init__(self, key=0, value=0):
        self.key = key
        self.value = value
        self.prev = None
        self.next = None


class LRUCache:
    def __init__(self, capacity: int):
        self.capacity = capacity
        self.cache = {}

        self.left = Node()
        self.right = Node()
        self.left.next = self.right
        self.right.prev = self.left

    def remove(self, node):
        prev_node = node.prev
        next_node = node.next
        prev_node.next = next_node
        next_node.prev = prev_node

    def insert(self, node):
        prev_node = self.right.prev
        prev_node.next = node
        node.prev = prev_node
        node.next = self.right
        self.right.prev = node

    def get(self, key: int) -> int:
        if key not in self.cache:
            return -1

        node = self.cache[key]
        self.remove(node)
        self.insert(node)
        return node.value

    def put(self, key: int, value: int) -> None:
        if key in self.cache:
            node = self.cache[key]
            node.value = value
            self.remove(node)
            self.insert(node)
            return

        node = Node(key, value)
        self.cache[key] = node
        self.insert(node)

        if len(self.cache) > self.capacity:
            lru = self.left.next
            self.remove(lru)
            del self.cache[lru.key]
```

No lambda functions are used.

## 7. Dry run

For capacity 2:

```text
put(1,10) -> [1]
put(2,20) -> [1,2]
get(1)    -> 10, order becomes [2,1]
put(3,30) -> evict 2, order [1,3]
get(2)    -> -1
```

The list is shown from LRU to MRU.

## 8. Complexity

- `get`: `O(1)` average.
- `put`: `O(1)` average.
- Space: `O(capacity)`.

Hash-map access is average O(1); linked-list remove/insert is worst-case O(1).

## 9. Correctness

Invariant: the linked list contains exactly the cached nodes ordered from least to most recently used, and the hash map points to those exact nodes. Every successful access moves its node to the MRU end. Every insertion starts as MRU. Therefore when the cache exceeds capacity, `left.next` is exactly the least recently used key and is the correct eviction target.

## 10. Edge cases and common mistakes

- Capacity 1.
- Updating an existing key should not increase cache size.
- `get` changes recency order.
- Repeated updates to the same key.

Common mistakes:
- using only a dictionary and trying to scan for oldest keys,
- using a singly linked list,
- forgetting to remove an existing node before reinserting it,
- evicting `right.prev` instead of `left.next`,
- storing only values in the map rather than node references.

## 11. Interviewer follow-ups

**Why not Python OrderedDict?** It solves the problem in practice, but interviews often expect the underlying hash-map + doubly-linked-list design.

**LFU cache?** Need frequency buckets plus recency ordering within each frequency, which is more complex.

**Thread safety?** Add synchronization around compound map/list mutations or use a concurrency-aware design.

**TTL expiration too?** Add expiration metadata and a separate structure such as a min-heap or timing wheel for expiry management.

## 12. What to say aloud

> “The O(1) requirement means one structure is not enough. A hash map gives direct key lookup, while a doubly linked list maintains recency and supports O(1) removal of arbitrary nodes. The map stores key-to-node references. I keep the LRU node next to a left sentinel and the MRU node next to a right sentinel. Every get or put moves the node to the MRU end; if capacity is exceeded, I remove the LRU node from both the list and map.”

## 13. Pattern takeaway

```text
Need O(1) lookup + mutable ordering
             ↓
Hash map alone: no order
Linked list alone: slow lookup
             ↓
Hash map -> node
Doubly linked list -> recency
             ↓
O(1) get and put
```
