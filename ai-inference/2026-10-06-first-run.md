# AI Inference Briefing — First Run

## 1. Disaggregated serving is becoming more operationally concrete

A recent vLLM engineering write-up describes splitting a monolithic inference server into separate prefill, decode, and CPU-only frontend responsibilities. The core motivation is that prefill and decode have very different bottlenecks: long prompts can hurt time-to-first-token and interfere with concurrent decode streams, while tokenization, parsing, and related request processing consume CPU resources that do not need to live on accelerator nodes.

Why this matters in practice: this shifts inference optimization from “make the kernel faster” toward “separate workloads so each stage can be scheduled and scaled independently.” For production systems, that means KV-cache transfer cost, stage balancing, frontend CPU sizing, and queueing behavior become first-class performance variables.

Worth reading:

https://github.com/vllm-project/vllm-project.github.io/blob/main/_posts/2026-09-29-disaggregated-serving-guide.md

## 2. CPU inference tuning in vLLM is increasingly explicit about NUMA and thread placement

Current vLLM CPU guidance recommends reserving CPU capacity for the serving framework instead of allowing inference threads to consume every core. It also recommends aligning tensor parallelism with NUMA topology and exposes CPU-specific controls for KV-cache sizing and OpenMP thread binding.

For AMD Zen CPUs specifically, the current guidance accepts BF16 and FP32 rather than FP16, with FP16 model declarations converted to BF16 at load time.

Why this matters for EPYC work: on large multi-socket or multi-NUMA systems, topology-aware placement can matter as much as individual operator speed. An optimized GEMM is not enough if request handling, KV-cache traffic, memory placement, or thread scheduling creates cross-NUMA traffic and contention.

Worth reading:

https://github.com/vllm-project/vllm/blob/main/docs/getting_started/installation/cpu.md

## 3. CPU serving performance work is moving beyond GEMM optimization

An Arm/vLLM engineering report from July is useful even if your primary platform is EPYC because of the methodology. Their profiling showed that dense layers were already spending substantial time in highly optimized BF16 GEMMs, so further end-to-end gains required work on allocator behavior, synchronization, framework overhead, attention kernels, quantized execution, threading, and CPU utilization.

Why this matters for your ZenDNN background: it reinforces an important systems lesson — once matrix multiplication approaches hardware efficiency, the bottleneck migrates. The next gains often come from reducing memory traffic, synchronization, dispatch overhead, allocation, attention cost, and orchestration inefficiencies.

Worth reading:

https://github.com/vllm-project/vllm-project.github.io/blob/main/_posts/2026-07-29-optimizing-vllm-on-arm-cpus.md

## 4. Quantization and MoE CPU support continue expanding

Recent vLLM release notes include CPU-side work such as additional MLA support for DeepSeek-family models, Triton-CPU packaging, quantization support on more architectures, BF16 MoE paths using ZenTorch on AMD, and optimizations around MXFP4 handling.

Why this matters: CPU inference is broadening beyond small dense transformer execution. MoE, low-bit formats, and newer attention structures increasingly need viable CPU paths. For enterprise deployments, this can expand the set of models that are practical on existing server fleets without requiring dedicated accelerators for every workload.

Worth reading:

https://github.com/vllm-project/vllm/releases

## 5. AMD continues positioning EPYC for both direct inference and host-side inference performance

AMD’s current EPYC 9005 inference material emphasizes small- and mid-size model deployment directly on server CPUs, while also highlighting the impact of host CPU performance in accelerator-based inference systems. The page also points to speculative decoding as one avenue for improving Llama-family inference performance.

Why this matters: there are two distinct CPU optimization opportunities. One is pure CPU inference. The other is optimizing the host side of heterogeneous GPU/accelerator serving, where request processing, preprocessing, orchestration, networking, and CPU-side stages can become bottlenecks even when token generation happens elsewhere.

Worth reading:

https://www.amd.com/en/products/processors/server/epyc/ai/9005-inference.html

## 6. Per-request observability itself has a CPU cost

vLLM now documents per-request timing metrics for SLA analysis, billing, and latency debugging, but explicitly warns that calculating them can introduce non-negligible CPU overhead at high concurrency.

Why this matters: instrumentation is part of the workload. When you benchmark an inference stack, especially on CPUs, measure with and without detailed telemetry. Otherwise observability overhead can be incorrectly attributed to model execution or serving-engine regressions.

Worth reading:

https://github.com/vllm-project/vllm/blob/main/docs/features/per_request_metrics.md

## Engineering implications to carry into your own work

The strongest theme is that CPU inference performance is increasingly a full-stack problem rather than a kernel-only problem. For an EPYC/ZenDNN-oriented engineer, I would pay particular attention to four layers together:

- Kernel efficiency: GEMM, attention, quantized kernels, fusion, vectorization.
- Memory/topology efficiency: NUMA placement, KV-cache locality, allocation behavior, bandwidth pressure.
- Serving architecture: prefill/decode separation, batching, scheduling, speculative decoding, request concurrency.
- Framework overhead: tokenization, parsing, synchronization, Python/runtime overhead, telemetry, and frontend CPU reservation.

A useful profiling question is therefore no longer just “which operator dominates?” but also “what percentage of end-to-end latency is outside optimized operators, and how does that change with concurrency?”

## What looks most consequential right now

The most important development to follow is the maturation of disaggregated serving combined with explicit CPU resource partitioning. If prefill, decode, and frontend processing can be independently scaled and placed, CPU optimization becomes relevant even in accelerator-heavy serving clusters. That creates a broader optimization surface for technologies around EPYC, ZenDNN, ZenTorch, NUMA-aware scheduling, and CPU-side preprocessing.

The next thing I would benchmark experimentally is the interaction between reserved frontend cores, inference-thread binding, NUMA-aware tensor parallelism, and p99 latency under rising concurrency. That experiment can reveal whether a system is compute-bound, bandwidth-bound, scheduler-bound, or frontend-bound far more clearly than single-request tokens/sec alone.
